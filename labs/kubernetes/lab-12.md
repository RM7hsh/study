# 🧪 Lab 12: Работа с конфиденциальными данными через Secrets

## 📋 Обзор

**Secret** — объект K8s, предназначенный для хранения чувствительных данных: паролей, токенов, приватных ключей или доступов к Registry. Как и ConfigMap, секреты можно прокидывать в контейнеры через переменные окружения или монтировать как файлы. Однако на диске ноды (внутри рантайма) секреты хранятся в оперативной памяти (`tmpfs`), что предотвращает их утечку при дампе физических дисков воркеров.

В этой лабораторной работе мы создадим секрет типа `Opaque` (универсальный тип), закодируем учетные данные для нашей базы, подключим их к веб-приложению и научимся безопасно декодировать их прямо из консоли.

## 🎯 Цели

* Понять разницу между кодированием (Base64) и реальным шифрованием.
* Создать `Secret` декларативным путем через YAML-манифест.
* Смонтировать секретные ключи в Под как переменные окружения (`env`) и как файлы (`volume`).
* Освоить быстрый CLI-декод секретов для проверки корректности данных.

## 📝 Пошаговые инструкции

### Шаг 1: Кодирование данных и создание манифеста

Для декларативного создания Секрета все значения в блоке `data` должны быть переведены в формат Base64. Самая частая ошибка здесь — захватить системный символ переноса строки (`\n`). Избавимся от него с помощью ключа `-n` у утилиты `echo`.

Выполнить на `k8s-master-01`:

```bash
mkdir -p ~/k8s-lab/lab12 && cd ~/k8s-lab/lab12

# 1. Кодируем логин и пароль в Base64
echo -n "db_admin_user" | base64
# Вывод (запомни его): ZGJfYWRtaW5fdXNlcg==

echo -n "P@ssw0rdMiddleLevel2026" | base64
# Вывод (запомни его): UEBzc3cwcmRNaWRkbGVMZXZlbDIwMjY=

```

Теперь соберем манифест `secret-database.yaml`. Используем тип `Opaque` (для произвольных секретов):

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
  namespace: work
type: Opaque
data:
  DB_USER: ZGJfYWRtaW5fdXNlcg==
  DB_PASS: UEBzc3cwcmRNaWRkbGVMZXZlbDIwMjY=

```

Примени манифест:

```bash
kubectl apply -f secret-database.yaml

# Проверяем наличие (кластер скроет значения, показав только размер в байтах)
kubectl get secret db-credentials -n work

```

### Шаг 2: Внедрение Секретов в приложение (Два метода)

Создадим `Deployment` для бэкенд-приложения. Одному контейнеру мы отдадим логин через переменную окружения, а пароль подкинем в виде защищенного файла на диске.

Создай файл `deployment-backend.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: backend-app
  namespace: work
spec:
  replicas: 1
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
      - name: app-container
        image: alpine:latest
        command: ["/bin/sh", "-c", "sleep 3600"]
        resources:
          requests:
            memory: "64Mi"
            cpu: "50m"
          limits:
            memory: "128Mi"
            cpu: "100m"
        
        # 🔓 Метод 1: Проброс ключа DB_USER в виде переменные окружения (ENV)
        env:
        - name: DATABASE_USER
          valueFrom:
            secretKeyRef:
              name: db-credentials
              key: DB_USER

        # 🔒 Метод 2: Монтирование всего секрета как защищенной папки/файла
        volumeMounts:
        - name: secret-volume
          mountPath: /etc/app/secrets
          readOnly: true
          
      volumes:
      - name: secret-volume
        secret:
          secretName: db-credentials
          items:
          - key: DB_PASS
            path: db_password.txt # Файл будет доступен по пути /etc/app/secrets/db_password.txt

```

Примени манифест:

```bash
kubectl apply -f deployment-backend.yaml

```

### Шаг 3: Верификация и проверка уровня защиты

Давай зайдем внутрь Пода и проверим, как рантайм `containerd` разложил наши секреты.

```bash
# Получаем имя пода
kubectl get pods -n work -l app=backend

# 1. Проверяем переменную окружения (значение должно автоматически декодироваться из Base64!)
kubectl exec -it <ИМЯ_ПОДА> -n work -- env | grep DATABASE_USER
# Ожидаемый вывод: DATABASE_USER=db_admin_user

# 2. Проверяем файл с паролем
kubectl exec -it <ИМЯ_ПОДА> -n work -- cat /etc/app/secrets/db_password.txt
# Ожидаемый вывод: P@ssw0rdMiddleLevel2026

```

**Мидл-анализ безопасности диска:**
Запусти внутри пода команду `mount | grep secrets`. Ты увидишь, что папка смонтирована как тип **`tmpfs`**. Это значит, что секрет лежит исключительно в RAM воркер-ноды. Если злоумышленник выдернет диск из сервера, секретов там не окажется.

### Шаг 4: Быстрое чтение секретов через CLI (Полезно для отладки)

Когда в проде что-то ломается (например, приложение пишет `Invalid Password`), мидл-инженер должен уметь быстро проверить, что именно записано в Секрете K8s, не заходя внутрь подов.

Используем JSONPath или утилиту `go-template` прямо в `kubectl`:

```bash
# Извлекаем и декодируем ключ DB_PASS на лету
kubectl get secret db-credentials -n work -o jsonpath="{.data.DB_PASS}" | base64 --decode

```

*Команда вернет чистый пароль без необходимости ковыряться в YAML.*

## 🔍 Инженерный траблшутинг Secrets (Middle-level)

1. **Приложение падает с ошибкой `blank password / invalid format`:**
* *Причина:* Самая частая беда — кодирование строки с помощью `echo "my_pass" | base64` (без флага `-n`). В Base64 улетает невидимый символ `\n` (перенос строки). На выходе получается хэш, содержащий лишний байт. Приложение пытается авторизоваться в базе с паролем, у которого в конце стоит невидимый Enter, и получает отказ.
* *Решение:* Всегда использовать `echo -n` или генерировать секрет императивно:
`kubectl create secret generic my-secret --from-literal=password=my_pass`.


2. **Ограничение прав доступа (RBAC):**
По умолчанию любой, у кого есть доступ к `kubectl` в данном неймсейсе, может прочитать Секрет через `jsonpath` (как в Шаге 4). Настоящий Middle настраивает политики RBAC так, чтобы разработчики имели права `get/list/watch` на ConfigMaps, но **не имели доступа** к ресурсу `secrets` (доступ к ним оставляют только сервис-аккаунтам деплойментов).
