# 🧪 Lab 5: Стратегии апдейта, Probes (Liveness/Readiness) и Rollback

## 📋 Обзор

Эта лабораторная работа переводит работу с `Deployments` на уровень Production-ready. Мы разберем стратегию плавного обновления `RollingUpdate`, внедрим пробы для проверки доступности приложения и научимся мгновенно откатывать сломанные релизы (`Rollback`), защищая трафик пользователей от аварий.

## 🎯 Цели

* Настроить тюнинг стратегии `RollingUpdate` (`maxSurge`, `maxUnavailable`).
* Внедрить **Readiness Probe** (готовность принимать трафик) и **Liveness Probe** (живучесть контейнера).
* Провести контролируемый апдейт версии приложения без единого потерянного запроса (Zero-Downtime).
* Симулировать выкатку «битого» релиза, зафиксировать зависание деплоймента и выполнить откат (`Rollout Undo`).

### Шаг 2: Создание отказоустойчивого манифеста (Mid-level)

Мы создадим веб-приложение, но теперь добавим в него логику управления жизненным циклом.

Создай файл `deployment-mid.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mid-web-app
  namespace: work
spec:
  replicas: 4
  # 1. Тюнинг стратегии обновления
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%        # На сколько подов можно превысить лимит replicas при апе (4 + 1 = 5 макс)
      maxUnavailable: 25%  # Сколько подов максимум может быть недоступно в процессе апдейта (4 - 1 = 3 мин)
  selector:
    matchLabels:
      app: prod-http
  template:
    metadata:
      labels:
        app: prod-http
    spec:
      containers:
      - name: web-core
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
        # Ограничения ресурсов (Requests/Limits)
        resources:
          requests:
            memory: "64Mi"
            cpu: "100m"
          limits:
            memory: "128Mi"
            cpu: "200m"
        
        # 2. Проверки работоспособности (Probes)
        # Readiness: Готово ли приложение отвечать пользователям? (Если упала — под убирается из балансировщика)
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5   # Ждать 5 сек после старта перед первой проверкой
          periodSeconds: 5          # Проверять каждые 5 сек
          successThreshold: 1       # Достаточно 1 успеха
          failureThreshold: 2       # После 2 ошибок под считается сломанным
        
        # Liveness: Жив ли сам процесс? (Если упала — Kubernetes принудительно перезапускает контейнер)
        livenessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 10  # Даем время приложению раскачаться
          periodSeconds: 10
          failureThreshold: 3

```

Примени манифест в кластер:

```bash
kubectl apply -f deployment-mid.yaml

# Проверяем статус развертывания
kubectl get deployment mid-web-app

```

Обрати внимание на колонку `READY` в процессе запуска. Поды перейдут в статус готовности только *после того*, как успешно отработает `readinessProbe`.

### Шаг 3: Zero-Downtime апдейт и история версий

Обновим версию Nginx с `1.25-alpine` на `1.26-alpine`. При этом мы хотим отслеживать шаги обновления.

```bash
# Меняем образ декларативно прямо через kubectl (мидл-вей для быстрых хотфиксов)
kubectl set image deployment/mid-web-app web-core=nginx:1.26-alpine --record=true

```

*(Флаг `--record=true` запишет нашу команду в историю ревизий, что критически важно для аудита).*

**Сразу же запускаем мониторинг репликации:**

```bash
kubectl rollout status deployment/mid-web-app

```

Ты увидишь, как плавно Kubernetes гасит старые поды и поднимает новые. За счет настроек `maxSurge` и `maxUnavailable` в системе всегда оставалось как минимум 3 живых пода, державших нагрузку.

Проверим историю версий:

```bash
kubectl rollout history deployment/mid-web-app

```

Вывод покажет две ревизии (Revision 1 и Revision 2).

### Шаг 4: Симуляция аварии (Выкатка битого релиза)

Представь, что джуниор/разработчик ошибся и запушил в деплоймент образ с несуществующим тегом, либо указал неверный порт для `readinessProbe` (например, порт 81, где никто не слушает). Наша проба начнет отвечать отказом.

Давай симулируем эту аварию:

```bash
# Накатываем битую версию (несуществующий образ)
kubectl set image deployment/mid-web-app web-core=nginx:broken-version --record=true

# Проверяем, что происходит с подами
kubectl get pods

```

**Что происходит на самом деле:**
Ты увидишь, что часть подов застряла в статусе `ErrImagePull` или `ImagePullBackOff`.
Но самое главное — **старый продакшн-сайт продолжает работать!** Наша стратегия `maxUnavailable: 25%` разрешила погасить только 1 старый под. Остальные 3 старых пода живы и обрабатывают трафик, потому что новые поды не прошли `readinessProbe` и Kubernetes заблокировал дальнейшую волну обновления.

---

### Шаг 5: Аварийный откат (Rollback)

Система видит аварию, деплоймент заблокирован. Твоя задача как мидла — мгновенно вернуть всё «как было» одной командой.

```bash
# Проверяем историю, чтобы понять, куда откатываться
kubectl rollout history deployment/mid-web-app

# Откатываемся на предыдущую стабильную ревизию (в данном случае на ревизию 2)
kubectl rollout undo deployment/mid-web-app --to-revision=2

# Проверяем статус восстановления
kubectl rollout status deployment/mid-web-app

```

Кластер мгновенно уничтожит сломанные заготовки и вернет полную емкость стабильных контейнеров Nginx `1.26-alpine`.

```bash
# Финальная проверка: все 4 пода снова Ready
kubectl get pods

```

## 🔍 Диагностика проблем уровня Middle (Troubleshooting)

При работе с пробами часто возникает ситуация, когда под падает по кругу.

* **Симптом:** `kubectl get pods` показывает `RESTARTS: 5` и статус `CrashLoopBackOff`.
* **Как искать причину:** Выполняем `kubectl describe pod <имя_пода>`.
* **На что смотреть:** Ищем блок `Events`. Если там написано:
`Warning  Unhealthy  Liveness probe failed: HTTP probe failed with statuscode: 500`
Это значит, что твой контейнер запустился успешно, но внутренний код приложения (например, коннект к базе данных) вернул ошибку 500. Kubernetes посчитал контейнер зомби-процессом и принудительно его перезапустил.
* *Решение:* Тюнить `initialDelaySeconds` (давать приложению больше времени на прогрев кэшей при старте) или чинить бэкенд.
