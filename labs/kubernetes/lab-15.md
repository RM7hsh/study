Безопасность на уровне пространства имен — это отлично, но теперь пора переходить к сетевой безопасности (L3/L4). По умолчанию в Kubernetes действует правило **Flat Network** (плоская сеть): абсолютно любой под из любого неймспейса может напрямую достучаться до любого другого пода по его IP-адресу.

В продакшене это огромная уязвимость. Если злоумышленник взломает твой публичный веб-сервер (Nginx Frontend), он сможет напрямую подключиться к базе данных PostgreSQL внутри кластера. Чтобы этого избежать, мидл-инженер настраивает **NetworkPolicies** (сетевые политики).

Поскольку в **Lab 2** мы развернули полноценный CNI-плагин **Calico**, наш кластер на Rocky Linux 10 полностью готов к аппаратной фильтрации трафика через iptables/IPVS на нодах.

Переходим к **Lab 15**. Работаем строго в неймспейсе `work`.

# 🧪 Lab 15: Сетевая безопасность и изоляция подов через NetworkPolicies

## 📋 Обзор

**NetworkPolicy** — это встроенный сетевой фаервол Kubernetes. Он работает по принципу *White-листинга* (все, что явно не разрешено — запрещено). Как только сетевая политика выбирает (`selects`) определенный под, этот под мгновенно изолируется от внешнего мира, и к нему могут пробиться только те поды, чьи метки (`labels`) или неймспейсы прописаны в правилах `Ingress`.

В этой лабораторной работе мы полностью изолируем нашу базу данных PostgreSQL (`pg-app` из Lab 10), заблокируем к ней доступ со всех сторон, а затем точечно разрешим коннект только для нашего бэкенда (`backend-app` из Lab 12).

## 🎯 Цели

* Понять механику изоляции трафика (Default Deny).
* Создать политику ограничения входящего трафика (`Ingress`) по меткам подов.
* Развернуть тестовые поды (саботажников) для проверки блокировок.
* Проверить работу сетевого фаервола Calico на Middle-уровне.

## 📝 Пошаговые инструкции

### Шаг 1: Подготовка окружения и запуск тестовых клиентов

Убедимся, что наша база данных PostgreSQL жива и имеет метку `app: postgres-cluster` (из Lab 10).
Теперь создадим двух клиентов в пространстве имен `work`:

1. **`frontend-prod`** — легитимное приложение (пропишем ему метку `role: backend`).
2. **`hacker-pod`** — условный взломщик (без нужных меток), который попытается украсть данные.

Выполнить на `k8s-master-01`:

```bash
mkdir -p ~/k8s-lab/lab15 && cd ~/k8s-lab/lab15

# 1. Запускаем легитимный под с нужной меткой
kubectl run frontend-prod --image=alpine:latest -n work --labels="role=backend" -- sleep 3600

# 2. Запускаем под-саботажник без меток безопасности
kubectl run hacker-pod --image=alpine:latest -n work --labels="role=untrusted" -- sleep 3600

# 3. Запускаем под в дефолтном неймсейсе (внешний нарушитель)
kubectl run external-attacker --image=alpine:latest -n default -- sleep 3600

```

Давай проверим, что до применения политик **все три пода** могут спокойно достучаться до порта Postgres (5432) через утилиту `nc` (netcat).

```bash
# Проверяем доступ с легитимного пода (должно успешно подключиться/таймаут по протоколу, но порт открыт)
kubectl exec -it frontend-prod -n work -- nc -zvw3 pg-headless 5432

# Проверяем доступ с хакерского пода (тоже свободно пускает!)
kubectl exec -it hacker-pod -n work -- nc -zvw3 pg-headless 5432

```

### Шаг 2: Создание NetworkPolicy "Default Deny" (Полная изоляция)

Лучшая практика DevSecOps — сначала полностью закрыть доступ к критическому объекту, а затем открывать его точечно.

Создай файл `network-policy-db.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-security-firewall
  namespace: work # Политика применяется внутри нашего неймсейса
spec:
  # На какие поды накладывать правила? На нашу базу данных!
  podSelector:
    matchLabels:
      app: postgres-cluster
  policyTypes:
  - Ingress # Фильтруем ТОЛЬКО входящий трафик (исходящий из БД наружу оставляем открытым)
  
  # Оставляем блок ingress ПУСТЫМ. Это означает: запретить ВСЕМ и ВСЯ.
  ingress: []

```

Примени манифест:

```bash
kubectl apply -f network-policy-db.yaml

```

### Шаг 3: Проверка режима полной изоляции

Давай повторно запустим сканирование портов с наших тестовых подов:

```bash
# Проверяем легитимный под
kubectl exec -it frontend-prod -n work -- nc -zvw3 pg-headless 5432

# Проверяем хакерский под
kubectl exec -it hacker-pod -n work -- nc -zvw3 pg-headless 5432

```

**Результат Middle-анализа:**
Оба запроса намертво зависнут и завершатся по таймауту (`timed out`). Сеть Calico перехватила пакеты на сетевых интерфейсах нод `veth` и мгновенно уничтожила их (Drop), не дав дойти до контейнера Postgres. База полностью изолирована.

### Шаг 4: Точечное открытие доступа для бэкенда

Теперь добавим в нашу политику `White-list`. Разрешим входящие пакеты на порт `5432` только для тех подов, у которых есть метка `role: backend` внутри пространства имен `work`.

Открой файл `network-policy-db.yaml` и перепиши его структуру:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-security-firewall
  namespace: work
spec:
  podSelector:
    matchLabels:
      app: postgres-cluster
  policyTypes:
  - Ingress
  ingress:
  # 🔓 НАЧИНАЕМ ОПИСЫВАТЬ ПРАВИЛА ДОСТУПА
  - from:
    - podSelector:
        matchLabels:
          role: backend # Пускать только поды с этой меткой!
    ports:
    - protocol: TCP
      port: 5432 # Открываем строго порт СУБД

```

Примени обновленную конфигурацию:

```bash
kubectl apply -f network-policy-db.yaml

```

### Шаг 5: Финальный тест безопасности

Проверяем, как разделился наш трафик внутри пространства имен `work`:

```bash
# 1. Тестируем легитимный фронтенд/бэкенд (role=backend)
kubectl exec -it frontend-prod -n work -- nc -zvw3 pg-headless 5432
# Ожидаемый вывод: pg-headless (10.244.x.x:5432) open! Доступ открыт!

# 2. Тестируем хакерский под (role=untrusted)
kubectl exec -it hacker-pod -n work -- nc -zvw3 pg-headless 5432
# Результат: Намертво висит. Пакеты блокируются!

# 3. Тестируем атаку из дефолтного неймсейса
kubectl exec -it external-attacker -n default -- nc -zvw3 pg-headless.work.svc.cluster.local 5432
# Результат: Блокировка! Трафик из других неймсейсов не пройдет, даже если у них будет такая метка.

```

Мы построили классический **сегмент Zero-Trust сети** вокруг базы данных.

## 🔍 Инженерный траблшутинг NetworkPolicies (Middle-level)

На практике сетевые политики — это главный источник криков разработчиков: *«Мы выкатили код, а он не видит соседний микросервис!»*.

1. **Политика применена, но ничего не блокируется:**
* *Причина:* Самая частая проблема bare-metal кластеров — использование дефолтного CNI (например, голого Flannel), который физически **не поддерживает NetworkPolicies**. Он просто игнорирует эти манифесты.
* *Решение:* Использовать Calico или Cilium. Так как мы в Lab 2 поставили Calico, у нас всё работает из коробки.


2. **Блокировка DNS-запросов:**
Если ты закроешь *исходящий* трафик пода (`Egress`), под перестанет видеть DNS-сервер CoreDNS. Контейнер не сможет отрезолвить имя `pg-headless`.
* *Правило мидла:* Если фильтруешь `Egress`, всегда добавляй правило, разрешающее исходящий UDP/TCP трафик на порт `53` в пространство имен `kube-system`.
