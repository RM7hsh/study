Слушай, а это просто монументальный проект! У тебя получился отличный, зрелый локальный DevOps-контур: полноценный Git-сервер, собственный Docker Registry, умный кэширующий прокси NORA (который будет спасать твой канал при частых сборках) и автоматизация через Webhook Relay. Перенос всего этого стека в отказоустойчивый Kubernetes кластер — это как раз задача уровня крепкого Middle/Senior DevOps.

По поводу твоего пожелания **использовать Docker вместо containerd**: решение вполне рабочее, особенно учитывая, что твой Gitea Runner активно использует маппинг `/var/run/docker.sock` для сборки контейнеров на хосте.

> **Важный архитектурный нюанс:** Начиная с версии Kubernetes 1.24, из него полностью удален встроенный компонент `dockershim`. Это значит, что напрямую управлять Docker кластер больше не умеет. Чтобы подружить Kubernetes v1.28+ и Docker Engine, нам понадобится прослойка **`cri-dockerd`** (от Mirantis). Она транслирует команды K8s в стандартный Docker API. Мы без проблем внедрим её в наш план.

## 🗺 Архитектурная карта миграции: Docker Compose → Kubernetes

Перед тем как писать манифесты, давай разберем, во что превратятся твои сервисы в кластере:

* **PostgreSQL** → `StatefulSet` с использованием нашего динамического `StorageClass: nfs-dynamic`. Скрипт `init-databases.sql` мы упакуем в `ConfigMap` и подмонтируем в папку инициализации СУБД.
* **Gitea Main и Gitea Actions** → Два независимых `Deployment` (или `StatefulSet`), диски которых (`/data`) будут автоматически нарезаться на твоем NFS-сервере.
* **NORA (Proxy Cache)** → `Deployment` + `Service` (ClusterIP). Конфиг `config.toml` выносим в `ConfigMap`. Для кэша пакетов затребуем жирный PVC на NFS.
* **Nginx** → **Уничтожаем как отдельный контейнер!** Его роль полностью заберет наш **NGINX Ingress Controller** (который мы разбирали в Lab 7). Он будет в одиночку слушать 80-й порт балансировщика и раскидывать трафик по трем FQDN доменам на основе правил Ingress.
* **Gitea Runner и Webhook Relay** → Изолированные `Deployments` внутри неймсейса `work`. Runner будет монтировать `/var/run/docker.sock` с физических нод, где теперь крутится Docker.

Крайне важно перевести Docker на драйвер управления ресурсами `systemd`, чтобы он не конфликтовал с Kubernetes, и сразу прописать туда адреса твоих будущих локальных регистров.

Создай/отрейдактируй файл `/etc/docker/daemon.json` на всех нодах:

```json

  "log-driver": "json-file",

  ]
}

```

Запусти и включи службу Docker:

```bash

sudo systemctl enable --now docker

```

### 3. Установка cri-dockerd (Мост между K8s и Docker)

Поскольку в официальных репозиториях Rocky Linux этого пакета нет, мы скачаем готовый бинарник и настроим для него systemd-юниты.

Выполни на **каждой** ноде:

```bash
# 1. Очищаем старые проблемные файлы
sudo rm -f /etc/systemd/system/cri-docker.*
cd /tmp

# 2. Скачиваем архив и ставим бинарник (без опасных масок rm -rf)
wget https://github.com/Mirantis/cri-dockerd/releases/download/v0.3.15/cri-dockerd-0.3.15.amd64.tgz
tar -xvf cri-dockerd-0.3.15.amd64.tgz
sudo install -o root -g root -m 0755 cri-dockerd/cri-dockerd /usr/local/bin/cri-dockerd
rm -rf cri-dockerd-0.3.15.amd64.tgz cri-dockerd/

# 3. Скачиваем systemd конфигурацию НАПРЯМУЮ в целевую папку от root
sudo curl -sSL https://raw.githubusercontent.com/Mirantis/cri-dockerd/master/packaging/systemd/cri-docker.socket -o /etc/systemd/system/cri-docker.socket
sudo curl -sSL https://raw.githubusercontent.com/Mirantis/cri-dockerd/master/packaging/systemd/cri-docker.service -o /etc/systemd/system/cri-docker.service

# 4. Выставляем жесткие правильные права и сбрасываем контекст SELinux
sudo chown root:root /etc/systemd/system/cri-docker.*
sudo chmod 644 /etc/systemd/system/cri-docker.*
sudo restorecon -v /etc/systemd/system/cri-docker.*

# 5. Правим путь к бинарнику
sudo sed -i 's|/usr/bin/cri-dockerd|/usr/local/bin/cri-dockerd|g' /etc/systemd/system/cri-docker.service

# 6. Перезапускаем systemd и активируем сокет
sudo systemctl daemon-reload
sudo systemctl enable --now cri-docker.socket cri-docker.service
```

### 4. Проверка готовности сокета

Убедись, что сокет успешно поднялся и слушает систему:

```bash
ls -la /var/run/cri-dockerd.sock

```

### Скрипт автоматизации `install-k8s-docker.sh`

Создайте этот файл в вашей рабочей директории (например, `~/k8s-lab/install-k8s-docker.sh`). Перед его запуском убедитесь, что в подпапке `files/` у вас лежат скачанные бинарники `kubeadm`, `kubelet`, `kubectl` и `crictl` версии v1.28.0, как мы делали в первой лабораторной.

```bash
cat > ~/k8s-lab/install-k8s-docker.sh <<'EOF'
#!/bin/bash
set -e

echo "[1/6] Отключение Swap и настройка безопасности"
swapoff -a
sed -i '/ swap / s/^/#/' /etc/fstab
systemctl stop firewalld || true
systemctl disable firewalld || true

# Разрешаем SELinux корректно работать с сокетами и прокси
setsebool -P haproxy_connect_any 1 || true

echo "[2/6] Настройка модулей ядра под сетевой мост"
cat > /etc/modules-load.d/kubernetes.conf <<MODULES
overlay
br_netfilter
MODULES
modprobe overlay
modprobe br_netfilter

echo "[3/6] Настройка параметров sysctl (маршрутизация пакетов)"
cat > /etc/sysctl.d/99-kubernetes.conf <<SYSCTL
net.bridge.bridge-nf-call-iptables = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward = 1
SYSCTL
sysctl --system

echo "[4/6] Установка исполняемых файлов Kubernetes"
if [ ! -d "files" ]; then
    echo "Ошибка: Директория 'files' с бинарниками не найдена!"
    exit 1
fi

install files/kubeadm /usr/local/bin/
install files/kubelet /usr/local/bin/
install files/kubectl /usr/local/bin/
if [ -f files/crictl ]; then install files/crictl /usr/local/bin/; fi

# Создание системных симлинков
ln -sf /usr/local/bin/kubeadm /usr/bin/kubeadm
ln -sf /usr/local/bin/kubectl /usr/bin/kubectl
ln -sf /usr/local/bin/kubelet /usr/bin/kubelet
ln -sf /usr/local/bin/crictl /usr/bin/crictl

echo "[5/6] Настройка утилиты отладки crictl под Docker сокет"
# Это позволит командам вроде 'crictl ps' и 'crictl pods' видеть контейнеры внутри Docker
cat > /etc/crictl.yaml <<CRICTL
runtime-endpoint: "unix:///var/run/cri-dockerd.sock"
image-endpoint: "unix:///var/run/cri-dockerd.sock"
timeout: 10
debug: false
pull-image-on-create: false
CRICTL

echo "[6/6] Настройка и активация службы kubelet"
cp files/kubelet.service /usr/lib/systemd/system/
mkdir -p /usr/lib/systemd/system/kubelet.service.d
cp files/10-kubeadm.conf /usr/lib/systemd/system/kubelet.service.d/

systemctl daemon-reload
systemctl enable kubelet

echo "=== Предварительная загрузка образов Kubernetes через Docker сокет ==="
# Указываем kubeadm качать образы через cri-dockerd, чтобы они падали напрямую в кэш Docker
kubeadm config images pull --kubernetes-version=v1.28.0 --cri-socket=unix:///var/run/cri-dockerd.sock

echo "ПОДГОТОВКА УЗЛА ДЛЯ РАБОТЫ С DOCKER ЗАВЕРШЕНА УСПЕШНО!"
EOF
chmod +x ~/k8s-lab/install-k8s-docker.sh

```

### ⚠️ Напоминание по конфигурации Systemd-юнитов (Проверьте перед запуском)

Убедитесь, что файлы `kubelet.service` и `10-kubeadm.conf`, которые лежат у вас в `~/k8s-lab/files/`, не содержат жесткого хардкода под старый рантайм. Они должны выглядеть стандартно, так как `kubeadm` сам пропишет флаг сокета в `kubeadm-flags.env` при инициализации.

**Файл `~/k8s-lab/files/10-kubeadm.conf`:**

```ini
[Service]
Environment="KUBELET_KUBECONFIG_ARGS=--bootstrap-kubeconfig=/etc/kubernetes/bootstrap-kubelet.conf --kubeconfig=/etc/kubernetes/kubelet.conf"
Environment="KUBELET_CONFIG_ARGS=--config=/var/lib/kubelet/config.yaml"
EnvironmentFile=-/var/lib/kubelet/kubeadm-flags.env
EnvironmentFile=-/etc/sysconfig/kubelet
ExecStart=
ExecStart=/usr/local/bin/kubelet $KUBELET_KUBECONFIG_ARGS $KUBELET_CONFIG_ARGS $KUBELET_KUBEADM_ARGS $KUBELET_EXTRA_ARGS

```
