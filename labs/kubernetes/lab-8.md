# 🧪 Lab 8: Постоянное хранилище данных через Persistent Volumes (PV) и Claims (PVC)

## 📋 Обзор

В реальных bare-metal кластерах (на базе наших нод Rocky Linux) у нас нет автоматических облачных дисков (как в AWS или GCP). Нам необходимо самостоятельно размечать дисковое пространство.

В этой лабораторной работе мы разберем **статическое выделение томов**. Мы создадим кластерный диск (**Persistent Volume**), затем затребуем его часть для нашего приложения в пространстве имен `work` через **Persistent Volume Claim**, подключим его к базе данных и проверим, что данные выживают после полного уничтожения подов.

## 🎯 Цели

* Понять разницу между уровнями абстракции: PV (диск админа) и PVC (запрос разработчика).
* Настроить локальное хранилище на воркер-нодах кластера.
* Создать и связать ресурсы PV (Cluster-wide) и PVC (Namespaced: `work`).
* Развернуть приложение с постоянным хранением данных, симулировать аварию и проверить сохранность данных.

## 📝 Пошаговые инструкции

### Шаг 1: Подготовка физического хранилища на воркер-ноде

Поскольку мы работаем в режиме bare-metal, сымитируем постоянный диск, создав выделенную директорию на одной из нод, где наше приложение будет хранить данные.

**Выполнить через SSH непосредственно на ноде `k8s-worker-01`:**

```bash
# Создаем папку для данных нашей будущей базы данных
sudo mkdir -p /mnt/data/db-storage

# Даем права, чтобы контейнеры могли туда писать данные
sudo chmod 777 /mnt/data/db-storage

```

---

### Шаг 2: Создание Persistent Volume (Кластерный уровень)

**Важно для понимания Middle-уровня:** `PersistentVolume` — это ресурс *всего кластера*. Он не принадлежит никакому неймспейсу. Это физический диск, который системный администратор отдает в пользование разработчикам.

Вернись на **`k8s-master-01`**, создай папку для лабораторной `mkdir -p ~/k8s-lab/lab8 && cd ~/k8s-lab/lab8` и опиши файл `pv-local.yaml`:

```yaml
apiVersion: v1
kind: PurePersistentVolume # Опечатка исключена, используем стандартный v1 класс:
kind: PersistentVolume
metadata:
  name: local-pv-storage
  labels:
    type: local
    usage: database
spec:
  storageClassName: manual # Имя класса хранилища (нужно для связывания)
  capacity:
    storage: 5Gi # Объем диска
  accessModes:
    - ReadWriteOnce # Диск может быть смонтирован на запись только одной нодой одновременно
  persistentVolumeReclaimPolicy: Retain # При удалении PVC данные на диске СОХРАНЯЮТСЯ
  hostPath:
    path: "/mnt/data/db-storage" # Путь на физической ноде, который мы подготовили в Шаге 1

```

Примени манифест:

```bash
kubectl apply -f pv-local.yaml

# Проверяем статус PV (он должен быть в статусе Available)
kubectl get pv local-pv-storage

```

### Шаг 3: Создание Persistent Volume Claim (Внутри namespace `work`)

Теперь мы выступаем в роли разработчиков приложения. Нам нужен диск на 2 Гигабайта внутри пространства имен `work`. Мы не знаем, где физически находятся диски, мы просто пишем запрос (Claim) к кластеру.

Создай файл `pvc-work.yaml`:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-pvc
  namespace: work # Строго в нашем рабочем пространстве имен!
spec:
  storageClassName: manual # Должно совпадать с storageClassName в PV
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 2Gi # Запрашиваем 2Гигабайта из доступных 5Гигабайт

```

Примени манифест:

```bash
kubectl apply -f pvc-work.yaml

# Проверяем статус запроса хранилища
kubectl get pvc -n work

```

**Мидл-анализ связывания (Binding):**
Как только ты применишь PVC, Kubernetes автоматически найдет подходящий по параметрам PV (свободный, с тем же `storageClassName` и объемом `>= 2Gi`) и свяжет их.

* Статус PVC изменится на `Bound`.
* Статус PV (если проверить через `kubectl get pv`) тоже изменится на `Bound`, и в колонке `CLAIM` появится запись `work/db-pvc`.

### Шаг 4: Развертывание Пода с монтированием хранилища

Развернем простую базу данных (например, Redis), которая будет использовать наше хранилище для сохранения снапшотов данных. Обязательно указываем ограничения ресурсов.

Создай файл `pod-db.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: redis-db
  namespace: work
  labels:
    role: db
spec:
  # Нам важно, чтобы под запустился именно на той ноде, где мы создали папку в Шаге 1!
  nodeName: k8s-worker-01 
  
  containers:
  - name: redis
    image: redis:7.2-alpine
    ports:
    - containerPort: 6379
    resources:
      requests:
        memory: "64Mi"
        cpu: "100m"
      limits:
        memory: "128Mi"
        cpu: "200m"
    volumeMounts:
    - name: redis-data
      mountPath: /data # Стандартный путь, куда Redis складывает файлы базы данных dump.rdb
  
  volumes:
  - name: redis-data
    persistentVolumeClaim:
      claimName: db-pvc # Указываем имя нашего PVC

```

Примени манифест:

```bash
kubectl apply -f pod-db.yaml

# Ждем запуска пода
kubectl get pod redis-db -n work

```

### Шаг 5: Тестирование персистентности (Сохранение данных)

Давай запишем данные в Redis, уничтожим под и проверим, что данные никуда не исчезли.

**1. Подключаемся к Redis и записываем тестовый ключ:**

```bash
kubectl exec -it redis-db -n work -- redis-cli

```

*Внутри CLI Redis выполни команды:*

```text
127.0.0.1:6379> set user_name "Rajabali_Muminshoevich"
OK
127.0.0.1:6379> save
OK
127.0.0.1:6379> exit

```

**2. Идем на ноду `k8s-worker-01` и проверяем появление файла на диске:**

```bash
ls -lh /mnt/data/db-storage/
# Ты увидишь файл dump.rdb. Физическая запись сработала!

```

**3. Имитируем падение/пересоздание пода на мастере:**

```bash
# Удаляем под базы данных принудительно
kubectl delete pod redis-db -n work

# Пересоздаем его заново из того же манифеста
kubectl apply -f pod-db.yaml
kubectl get pod redis-db -n work -w

```

**4. Проверяем сохранность данных после «аварии»:**

```bash
kubectl exec -it redis-db -n work -- redis-cli

```

*Запрашиваем наш ключ:*

```text
127.0.0.1:6379> get user_name
"Rajabali_Muminshoevich"
127.0.0.1:6379> exit

```

Данные на месте! Под полностью переродился, но за счет PVC мгновенно подмонтировал старый физический диск с Rocky Linux ноды.

## 🔍 Инженерный траблшутинг хранилищ (Middle-level)

На практике диски «застревают» чаще всего. Вот основные проблемы, которые мидл должен решать мгновенно:

1. **PVC застрял в статусе `Pending`:**
Это значит, что Kubernetes не смог найти ни одного PV для этого запроса.
* *Как лечить:* Проверь `kubectl describe pvc <имя>`. Смотри ошибки. Частые причины: не совпадает `storageClassName`, запрашиваемый объем в PVC больше, чем есть на PV (например, PV на 2Gi, а PVC просит 5Gi), либо этот PV уже занят другим PVC (так как режим `ReadWriteOnce` отдает диск только одному клейму).


2. **Под застрял в статусе `ContainerCreating` или `Terminating`:**
* *Причина:* Проблема блокировки тома (Volume Lock). Если под переезжает на другую ноду, старая нода может не успеть "отпустить" диск. В bare-metal с `hostPath` или `local` томами под жестко привязан к конкретной ноде. Если ты не укажешь `nodeName` или `nodeAffinity`, планировщик может закинуть под на `worker-02`, где физически папки `/mnt/data/db-storage` нет, и под зависнет.

## ✅ Критерии успешного выполнения лабораторной работы

1. PV успешно создан на глобальном уровне, а PVC — в пространстве имен `work`.
2. Статус обоих ресурсов находится в состоянии `Bound`.
3. База данных Redis успешно стартовала и использует постоянный том.
4. Продемонстрировано выживание данных (`user_name`) после полного удаления объекта Пода.
