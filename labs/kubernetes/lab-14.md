Погнали! Автоматизация — это круто, но без жесткого контроля аппетитов приложений автоматический CronJob или взбесившийся Deployment могут легко выжрать все ресурсы твоих нод Rocky Linux, уложив соседние системные поды (например, тот же Calico или CoreDNS).

До этого момента мы прописывали `requests` и `limits` вручную в каждом манифесте. Но надеяться на человеческий фактор в проде нельзя — кто-то обязательно забудет указать лимиты. На уровне Middle-инженера ты должен уметь настраивать автоматическую страховку: **LimitRanges** (дефолтные лимиты «для забывчивых») и **ResourceQuotas** (жесткий потолок на весь неймспейс).

Переходим к **Lab 14**. Работаем строго в пространстве имен `work`.

# 🧪 Lab 14: Управление лимитами неймспейса (LimitRanges и ResourceQuotas)

## 📋 Обзор

Если представить пространство имен `work` как коммунальную квартиру внутри нашего кластера, то **ResourceQuota** — это счетчик, который ограничивает суммарное потребление ресурсов всей квартиры (например, не более 2 ядер CPU и 3 Гб оперативной памяти на всех). **LimitRange** — это правила внутреннего распорядка: они определяют минимальный и максимальный размер одного пода, а также автоматически выдают «паек» (дефолтные лимиты) контейнеру, если разработчик поленился прописать их в манифесте.

## 🎯 Цели

* Настроить жесткую квоту ресурсов (`ResourceQuota`) на пространство имен `work`.
* Создать правила автоматического квотирования (`LimitRange`).
* Проверить механизм автоматической инжекции лимитов в «голые» поды.
* Протестировать блокировку API-сервера при попытке превысить квоту неймспейса.

---

## 📝 Пошаговые инструкции

### Шаг 1: Создание ResourceQuota (Потолок для неймспейса)

Мы ограничим наш рабочий неймспейс, чтобы он суммарно не мог запросить больше 2 ядер CPU и 2 Гигабайт RAM, а также ограничим общее число подов до 10.

Выполнить на `k8s-master-01`:

```bash
mkdir -p ~/k8s-lab/lab14 && cd ~/k8s-lab/lab14

# Создаем маниfeст quota.yaml
cat > quota.yaml <<EOF
apiVersion: v1
kind: ResourceQuota
metadata:
  name: work-namespace-quota
  namespace: work
spec:
  hard:
    pods: "10"                  # Максимум 10 подов в этом неймспейсе
    requests.cpu: "1"           # Сумма всех requests.cpu не может превысить 1 ядро (1000m)
    requests.memory: "1Gi"      # Сумма всех requests.memory не может превысить 1 Гигабайт
    limits.cpu: "2"             # Сумма всех limits.cpu не может превысить 2 ядра
    limits.memory: "2Gi"        # Сумма всех limits.memory не может превысить 2 Гигабайта
EOF

kubectl apply -f quota.yaml

```

Давай проверим, сколько ресурсов наш неймспейс `work` потребляет прямо сейчас (с учетом запущенных Postgres и бэкаперов из прошлых лаб):

```bash
kubectl get resourcequota work-namespace-quota -n work

```

В выводе в колонке `USED` ты увидишь текущую утилизацию, а в `HARD` — наши новые лимиты. Если текущие поды уже превышают квоту, кластер позволит им доработать, но новые поды ты запустить не сможешь.

---

### Шаг 2: Создание LimitRange (Автоматические лимиты)

Теперь настроим автоматическую подстановку лимитов для контейнеров, у которых они не указаны.

Создай файл `limits.yaml`:

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: work-container-limits
  namespace: work
spec:
  limits:
  - type: Container
    # 1. Дефолтные лимиты, которые пропишутся АВТОМАТИЧЕСКИ, если их забыли указать
    default:
      memory: "128Mi"
      cpu: "200m"
    # 2. Дефолтные запросы (requests), которые пропишутся автоматически
    defaultRequest:
      memory: "64Mi"
      cpu: "100m"
    # 3. Валидация: контейнер меньше этого размера создать будет НЕЛЬЗЯ
    min:
      memory: "32Mi"
      cpu: "50m"
    # 4. Валидация: контейнер больше этого размера создать будет НЕЛЬЗЯ
    max:
      memory: "512Mi"
      cpu: "500m"

```

Примени манифест:

```bash
kubectl apply -f limits.yaml

```

### Шаг 3: Тестирование LimitRange (Магия авто-подстановки)

Давай проверим, как кластер защищает нас от «забывчивых» разработчиков. Запустим абсолютно "голый" под веб-сервера без единого упоминания блоков `resources`.

```bash
# Запускаем императивно простой под
kubectl run naked-nginx --image=nginx:1.25-alpine -n work

# Сразу же смотрим его внутреннюю конфигурацию
kubectl describe pod naked-nginx -n work

```

**Мидл-анализ вывода:**
Найди блок `Containers -> Limits/Requests`. Ты увидишь, что Kubernetes самостоятельно, прямо на лету во время прохождения запроса через Mutation Admission Controller, вшил в этот под наши настройки:

```text
    Limits:
      cpu:     200m
      memory:  128Mi
    Requests:
      cpu:     100m
      memory:  64Mi

```

Под успешно прошел валидацию и запустился!

### Шаг 4: Тестирование ResourceQuota (Проверка на прочность)

А теперь попробуем сломать систему и сымитировать ситуацию, когда деплоймент пытается масштабироваться, сжирая больше ресурсов, чем ему выделено на весь неймспейс.

Создадим «жадный» деплоймент, который просит сразу много ресурсов. Создай файл `greedy-deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: greedy-apps
  namespace: work
spec:
  replicas: 5 # 5 реплик по 400Mi лимита = 2000Mi (2Gi). Это сожрет весь наш лимит под завязку!
  selector:
    matchLabels:
      app: greedy
  template:
    metadata:
      labels:
        app: greedy
    spec:
      containers:
      - name: ubuntu-heavy
        image: ubuntu:latest
        command: ["sleep", "3600"]
        resources:
          requests:
            memory: "256Mi"
            cpu: "200m"
          limits:
            memory: "400Mi"
            cpu: "400m"

```

Примени манифест:

```bash
kubectl apply -f greedy-deployment.yaml

```

Теперь проверяем статус подов и самого деплоймента:

```bash
kubectl get deployment greedy-apps -n work
kubectl get pods -n work

```

**Что произошло:**
Ты увидишь, что деплоймент смог поднять только часть подов (или вообще ни одного, если твои старые поды Postgres уже заняли квоту). Часть подов просто не родилась.

Давай проведем глубокий аудит и посмотрим, где застряли поды. Смотрим логи подчиненного объекта `ReplicaSet`:

```bash
# Находим имя репликасета
kubectl get rs -n work

# Смотрим его описание
kubectl describe rs <ИМЯ_REPLICASET> -n work

```

В секции `Events` ты увидишь железный отказ API-сервера:

> `Warning  FailedCreate  ...  (combined from similar events): pods "greedy-apps-xxxxxxxx-" is forbidden: exceeded quota: work-namespace-quota, requested: requests.memory=256Mi, used: requests.memory=960Mi, limited: requests.memory=1Gi`

Планировщик и контроллер жестко заблокировали создание контейнеров, сохранив стабильность кластера и не дав выселить критически важные поды из соседних пространств имен.

## 🔍 Инженерный траблшутинг (Middle-level)

1. **Поды не создаются, но в `kubectl get pods` нет никаких ошибок:**
* *Где искать причину:* Ошибки превышения лимитов неймспейса никогда не пишутся в сам объект `Pod`, потому что до создания самого Пода дело даже не доходит. API-сервер рубит запрос на корню. Смотри всегда `kubectl describe rs <имя>` (для Deployments) или `kubectl describe statefulset <имя>`.


2. **Как очистить квоту, если нужно срочно выкатить фикс?**
Если продакшн заблокирован из-за квоты, у мидла есть два пути: либо быстро смигрировать/загасить старые ненужные поды (`kubectl delete pod naked-nginx -n work`), либо временно расширить параметры в `quota.yaml` и сделать `kubectl apply -f quota.yaml`.
