# 🧪 Lab 6: Сетевое взаимодействие через Сервисы (ClusterIP и NodePort)
Сети в Kubernetes — это фундамент, на котором держится вся отказоустойчивость и балансировка. Поды эфемерны: они рождаются, умирают, меняют свои IP-адреса. Мидл-инженер должен уметь организовывать для них стабильные точки входа.
## 📋 Обзор

В этой лабораторной работе мы разберем абстракцию **Service (Сервис)**. Мы создадим внутренний балансировщик трафика (`ClusterIP`), проверим, как работает обнаружение сервисов через CoreDNS, а затем настроим `NodePort` для доступа к приложению с твоей физической машины или MacBook через IP-адреса нод Rocky Linux.

## 🎯 Цели

* Понять механику связи Сервиса и Подов через `Selectors` и `Endpoints`.
* Развернуть и протестировать внутренний сервис типа `ClusterIP`.
* Проверить работу Kube-DNS / CoreDNS внутри пространства имен `work`.
* Развернуть сервис типа `NodePort`, открыть выделенный порт в диапазоне `30000-32767` и проверить внешнюю доступность.

### Шаг 2: Создание и разбор Сервиса ClusterIP (Внутренний балансировщик)

`ClusterIP` — это дефолтный тип сервиса. Он создает единый, неизменяемый виртуальный IP-адрес внутри кластера. Трафик, прилетающий на этот IP, `kube-proxy` распределяет по подам.

Создай файл `service-clusterip.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: internal-web-svc
  namespace: work
spec:
  type: ClusterIP
  selector:
    app: prod-http # Сервис будет искать поды с этой меткой
  ports:
  - name: http
    protocol: TCP
    port: 8080      # Порт, который будет слушать сам Сервис
    targetPort: 80  # Порт, который слушает Nginx внутри контейнера

```

Примени манифест:

```bash
kubectl apply -f service-clusterip.yaml

```

**Мидл-анализ: Как Сервис находит Поды?**
Сервис не связывается с подами напрямую. Он создает вспомогательный объект — **Endpoints**.

```bash
# Проверяем созданный сервис
kubectl get svc internal-web-svc

# Проверяем, на какие IP-адреса подов он указывает
kubectl get endpoints internal-web-svc

```

В графе `ENDPOINTS` ты должен увидеть список IP-адресов (из сети Calico) всех твоих 4 подов деплоймента. Если там пусто (`<none>`), значит, ты ошибся в блоке `selector` (метки сервиса не совпадают с метками подов).

### Шаг 3: Проверка DNS-имен внутри неймсейса `work`

В Kubernetes встроен собственный DNS-сервер (CoreDNS). Каждый раз, когда создается сервис, он получает внутреннее доменное имя формата: `<имя-сервиса>.<неймспейс>.svc.cluster.local`.

Давай запустим отладочный под внутри пространства `work` и попробуем достучаться до нашего веб-сервера по имени.

```bash
# Запускаем временный под с утилитами curl/nslookup и проваливаемся в него
kubectl run net-test --image=curlimages/curl --restart=Never -it -- /bin/sh

```

**Выполняй команды НАХОДЯСЬ ВНУТРИ тестового пода `net-test`:**

```bash
# 1. Делаем запрос по ClusterIP (подставь IP своего сервиса из Шага 2)
curl http://<CLUSTER-IP>:8080

# 2. Делаем запрос по короткому DNS-имени (так как мы в одном неймсейсе work)
curl http://internal-web-svc:8080

# 3. Делаем запрос по полному FQDN-имени (если бы мы стучались из другого неймсейса)
curl http://internal-web-svc.work.svc.cluster.local:8080

exit

```

*После выхода удали тестовый под:* `kubectl delete pod net-test`.

### Шаг 4: Вывод приложения наружу через NodePort

`ClusterIP` работает только внутри K8s. Чтобы запросы пошли из твоей реальной домашней/рабочей сети, мы трансформируем сервис в тип `NodePort`. Он откроет одинаковый порт на **всех** физических нодах кластера (`192.168.77.181..187`).

Создай файл `service-nodeport.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-web-svc
  namespace: work
spec:
  type: NodePort
  selector:
    app: prod-http
  ports:
  - name: http
    protocol: TCP
    port: 80        # Порт сервиса внутри кластера
    targetPort: 80  # Порт контейнера
    nodePort: 32080 # Внешний порт (если не указать, K8s выберет рандомный из 30000-32767)

```

Примени манифест:

```bash
kubectl apply -f service-nodeport.yaml

```

Проверь статус распределения портов:

```bash
kubectl get svc external-web-svc

```

В колонке `PORT(S)` ты увидите сопоставление `80:32080/TCP`.

---

### Шаг 5: Проверка внешней доступности кластера

Теперь закрой терминал мастера и перейди на свой локальный хост (MacBook / ПК). Открой браузер или выполни `curl` к **любой** ноде твоего кластера на порт `32080`:

```bash
# Проверка через master-01
curl http://192.168.77.181:32080

# Проверка через worker-01 (даже если под не запущен на этой ноде, kube-proxy перенаправит трафик куда надо!)
curl http://192.168.77.186:32080

```

Ты увидишь заветный `Welcome to nginx!`.

> **Почему это работает?** Даже если на ноде `worker-01` физически нет подов твоего приложения, `kube-proxy` на этой ноде ловит пакеты на порту 32080, переводит их через iptables/IPVS в виртуальный ClusterIP, а сеть Calico перебрасывает трафик через туннель на ту ноду, где под реально запущен.

## 🔍 Инженерный траблшутинг сетей (Middle-level)

Самая частая проблема мидла на собеседованиях и в проде — **«Сервис запущен, но выдает ошибку 503 или таймаут»**.

**Чек-лист для проверки:**

1. **Смотри селекторы:** Выполни `kubectl describe svc <имя-сервиса>`. Проверь строку `Selector`. Она должна в точности (символ в символ, регистр важен) совпадать с тем, что написано в `labels` у подов.
2. **Проверяй порты:** Убедись, что `targetPort` в сервисе равен `containerPort` в деплойменте. Если Nginx слушает порт 80, а ты в `targetPort` указал 8080, сервис будет слать трафик в пустоту.
3. **Защита Rocky Linux:** Если `curl` изнутри кластера работает, а снаружи на порт `32080` не пускает — твоя ОС блокирует порты. Убедись, что на нодах выключен `firewalld` (`sudo systemctl status firewalld`), либо добавь правило:
`sudo firewall-cmd --add-port=32080/tcp --permanent && sudo firewall-cmd --reload`.

## ✅ Критерии успешного выполнения лабораторной работы

1. В неймсейсе `work` работают два сервиса: внутренний и внешний.
2. Команда `kubectl get endpoints` показывает актуальные IP подов для обоих сервисов.
3. Доменное имя `internal-web-svc` успешно резолвится внутри кластера.
4. Веб-страница Nginx открывается из внешней сети через IP любой ноды на порту 32080.

Логика движения трафика теперь у тебя в руках. Но в реальном продакшене `NodePort` используют редко, потому что портов мало (всего до 32767), а плодить IP-адреса нод неудобно. Для "взрослой" маршрутизации используют `Ingress`.
