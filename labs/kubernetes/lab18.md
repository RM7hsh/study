До сих пор мы вручную управляли горой YAML-файлов: для одного приложения нам приходилось поддерживать `deployment.yaml`, `service.yaml`, `configmap.yaml`, `networkpolicy.yaml`. Для решения этой проблемы на уровне Middle+ инженера используется **Helm** — официальный пакетный менеджер для Kubernetes. Он позволяет превратить статические YAML-файлы в динамические шаблоны (**Charts**), вынести все изменяемые настройки в один файл конфигурации (`values.yaml`) и управлять релизами как в обычном пакетном менеджере (с возможностью апгрейда и отката одной командой).

# 🧪 Lab 18: Пакетирование приложений и управление релизами через Helm

## 📋 Обзор

Инфраструктура Helm-чарта состоит из трех ключевых элементов:

1. **Папка `templates/**` — здесь лежат твои стандартные YAML-манифесты, но вместо хардкодных значений (например, `replicas: 3`) там прописаны шаблоны вида `{{ .Values.replicaCount }}`.
2. **Файл `values.yaml**` — главный и единственный файл настроек для разработчика. Все переменные, порты, лимиты ресурсов и теги образов для разных сред меняются только здесь.
3. **Файл `Chart.yaml**` — метаданные твоего пакета (имя, версия чарта, версия приложения).

В этой работе мы установим Helm, сгенерируем собственный чарт для веб-приложения со встроенными жесткими лимитами, научимся кастомизировать его под неймспейс `work`, обновим релиз и проведем безопасный откат.

## 🎯 Цели

* Установить бинарный файл Helm CLI на мастер-ноду.
* Создать и разобрать структуру собственного кастомного чарта.
* Параметризовать манифесты Deployment и Service через переменные `Values`.
* Развернуть приложение, провести контролируемый апгрейд (`Helm Upgrade`) и изучить историю релиза.

### Шаг 3: Параметризация манифестов (Шаблонизация)

Давай отредактируем файлы внутри `templates/`, чтобы они брали настройки из переменных.

**1. Настроим Сервис (`templates/service.yaml`):**
Открой файл через `nano` и приведи его к лаконичному виду, жестко зафиксировав наш рабочий тип ClusterIP, но сделав порты динамическими:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: {{ .Release.Name }}-svc
  namespace: work # Наш целевой неймспейс
spec:
  type: ClusterIP
  ports:
    - port: {{ .Values.service.port }}
      targetPort: http
      protocol: TCP
      name: http
  selector:
    app: {{ .Release.Name }}-web

```

**2. Настроим Деплоймент (`templates/deployment.yaml`):**
Перепишем деплоймент так, чтобы количество реплик, образ и лимиты ресурсов полностью управлялись извне:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-deploy
  namespace: work
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Release.Name }}-web
  template:
    metadata:
      labels:
        app: {{ .Release.Name }}-web
    spec:
      containers:
        - name: web-core
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 80
              protocol: TCP
          # Настраиваем пробы, которые мы изучили в Lab 5
          readinessProbe:
            httpGet:
              path: /
              port: 80
          resources:
            # Динамически пробрасываем блоки лимитов
            requests:
              cpu: {{ .Values.resources.requests.cpu }}
              memory: {{ .Values.resources.requests.memory }}
            limits:
              cpu: {{ .Values.resources.limits.cpu }}
              memory: {{ .Values.resources.limits.memory }}

```

### Шаг 5: Валидация и первый деплой релиза

Перед установкой чарта в продакшн мидл-инженер всегда проверяет синтаксис шаблонов (Linter) и запускает симуляцию деплоя (`Dry-run`).

```bash
# 1. Проверяем YAML-синтаксис и маппинг переменных
helm lint .

# 2. Запускаем Dry-Run (выведет готовые скомпилированные манифесты без отправки в кластер)
helm install stage-release . --dry-run --namespace work

# 3. Накатываем реальный релиз с именем "stage-release" в неймспейс "work"
helm install stage-release . --namespace work

```

Проверяем статус развертывания через стандартный CLI и через Helm:

```bash
# Helm покажет статус REVISION: 1
helm list --namespace work

# Сущности K8s создались с префиксом нашего релиза
kubectl get deployments,services,pods -n work -l app=stage-release-web

```

### Шаг 6: Управление жизненным циклом (Upgrade и History)

Представь, что пришла задача от бизнеса: нужно обновить версию Nginx до `1.26-alpine` и увеличить количество реплик до 4.

Вместо правок манифестов мы просто обновляем файл `values.yaml` (или передаем параметры прямо в командной строке, что чаще всего делают CI/CD пайплайны типа GitLab CI или GitHub Actions).

```bash
# Обновляем релиз на лету, меняя параметры через флаг --set
helm upgrade stage-release . --set replicaCount=4 --set image.tag=1.26-alpine --namespace work

```

Давай посмотрим, как Helm зафиксировал изменения:

```bash
helm history stage-release --namespace work

```

В выводе ты увидишь две ревизии (`REVISION 1` и `REVISION 2`). Контроллер плавно погасил старые контейнеры и накатил новые без простоя сети (Zero-Downtime).

---

### Шаг 7: Мгновенный откат релиза (Rollback)

Если в новой версии приложения обнаружился баг, Helm позволяет откатить весь стек (включая связанные сервисы и конфиги) обратно к любой стабильной ревизии одной командой:

```bash
# Откатываемся обратно на ревизию 1
helm rollback stage-release 1 --namespace work

# Проверяем историю — теперь активна REVISION 3 (копия первой ревизии)
helm history stage-release --namespace work

# Проверяем, что количество подов вернулось к 3, а образ — к 1.25
kubectl describe deployment stage-release-deploy -n work | grep Image

```

## 🔍 Инженерный траблшутинг Helm (Middle-level)

1. **Релиз застрял в статусе `FAILED`:**
* *Причина:* Если при обновлении (`helm upgrade`) новые поды не смогли запуститься (например, упали по `OOMKilled` или не прошли `ReadinessProbe`), Helm заблокирует релиз и пометит его как битый. Повторный запуск `helm upgrade` выдаст ошибку `another operation is in progress`.
* *Решение:* Сначала выполни `helm rollback <имя_релиза> <номер_прошлой_рабочей_ревизии>`, чтобы вернуть кластер в стабильное состояние, найди причину падения подов через `kubectl describe/logs`, исправь переменные в `values.yaml` и только потом запускай деплой заново.


2. **Как посмотреть итоговый YAML, который Helm сгенерировал прямо сейчас в кластере?**
```bash
helm get manifest stage-release --namespace work

```


*Утилита выведет чистый скомпилированный код из etcd.*
