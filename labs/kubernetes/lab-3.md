# 🧪 Lab 3: Создание и управление Pods

## 📋 Обзор

Эта лабораторная работа посвящена фундаментальному объекту Kubernetes — **Pod (Под)**. Вы научитесь запускать контейнеры императивным и декларативным путями, изучите внутреннюю сетевую структуру Пода, разберете работу с мультиконтейнерными паттернами (Sidecar) и освоите базовые команды инспекции и отладки.

* Развернуть мультиконтейнерный Под с общей сетевой и дисковой инфраструктурой.

## 📝 Пошаговые инструкции

### Шаг 1: Императивное создание Пода (Быстрый старт)

Императивный метод идеален для быстрой проверки гипотез, пингов сети или генерации базовых шаблонов.

**Выполнить на `k8s-master-01`:**

```bash
# Запуск одиночного Пода с веб-сервером Nginx
kubectl run quick-web --image=nginx:1.25-alpine --port=80

# Проверка статуса запуска в реальном времени
kubectl get pods quick-web -w

```

Дождитесь перехода в статус `Running`. Теперь соберем базовую информацию о том, где именно в кластере приземлился наш контейнер:

```bash
# Получение расширенной информации (IP и Нода размещения)
kubectl get pods quick-web -o wide

```

> **Интересный факт:** Обратите внимание, что IP-адрес Пода выдан из нашей сети Calico (`10.244.x.x`). Этот IP доступен напрямую с любой ноды кластера, но полностью изолирован от вашей внешней физической сети `192.168.77.x`.

### Шаг 2: Генерация и разбор Декларативного манифеста

В Production-среде инфраструктура всегда описывается кодом (IaC). Чтобы не писать YAML-файлы с нуля, заставим `kubectl` сделать черновик за нас.

```bash
# Создание папки для лабораторной работы
mkdir -p ~/k8s-lab/lab3 && cd ~/k8s-lab/lab3

# Генерация чистого манифеста без отправки запроса в API (Dry-Run режим)
kubectl run declarative-web --image=nginx:1.25-alpine --port=80 --dry-run=client -o yaml > pod-nginx.yaml

```

Откройте сгенерированный файл `pod-nginx.yaml` в редакторе `nano` и приведите его к каноническому виду, добавив метки и ограничения по ресурсам:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: declarative-web
  namespace: default
  labels:
    app: web-server
    tier: frontend
  annotations:
    description: "Main web server for testing Pod lifecycle"
spec:
  containers:
  - name: nginx-container
    image: nginx:1.25-alpine
    ports:
    - containerPort: 80
      name: http-port
    resources:
      requests:
        memory: "64Mi"
        cpu: "100m"
      limits:
        memory: "128Mi"
        cpu: "200m"

```

Примените манифест в кластер:

```bash
kubectl apply -f pod-nginx.yaml

```

### Шаг 3: Инспекция, логирование и отладка

Теперь применим навыки системного администратора для глубокого анализа запущенных объектов.

**1. Детальное описание состояния (События):**
Если Под не запускается, первая команда для траблшутинга — `describe`. Она показывает конфигурацию и, главное, ленту событий (Events) на самом низу вывода.

```bash
kubectl describe pod declarative-web

```

**2. Чтение системных логов контейнера:**

```bash
# Просмотр логов в реальном времени (аналог tail -f)
kubectl logs declarative-web -f

# Получение последних 20 строк логов
kubectl logs declarative-web --tail=20

```

**3. Интерактивная сессия (Выполнение команд внутри Пода):**
Провалимся внутрь контейнера, работающего на Rocky Linux базовой ноды, чтобы проверить его внутреннее окружение.

```bash
kubectl exec -it declarative-web -- /bin/sh

# Внутри контейнера: проверяем версию ОС и сетевые интерфейсы
nginx -v
cat /etc/os-release
exit

```

**4. Временный проброс портов (Port-Forwarding):**
Чтобы проверить работу веб-сервера прямо с вашей мастер-ноды (или локального ПК) без создания сервисов, можно временно "привязать" порт контейнера к локальному порту.

```bash
# Забрасываем порт 80 контейнера на порт 8080 мастера
kubectl port-forward pod declarative-web 8080:80

```

> **Тест:** Откройте вторую SSH-сессию к `k8s-master-01` и выполните `curl http://127.0.0.1:8080`. Вы увидите стандартную приветственную страницу Nginx. Для завершения проброса в первой сессии нажмите `Ctrl+C`.

### Шаг 4: Продвинутый уровень — Мультиконтейнерный Под (Паттерн Sidecar)

Контейнеры внутри одного Пода делят между собой **один и тот же сетевой стек (Network Namespace)** и могут делить **дисковые разделы (Volumes)**. Они видят друг друга через `localhost`.

Создадим Под, где основной контейнер генерирует логи, а Sidecar-контейнер непрерывно отправляет их в стандартный поток вывода.

Создайте файл `pod-sidecar.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
  labels:
    app: monitoring-test
spec:
  containers:
  - name: main-app
    image: alpine:latest
    command: ["/bin/sh", "-c"]
    args:
    - >
      while true; do
        echo "$(date) | INFO | Transaction successful." >> /var/log/app/transaction.log;
        sleep 3;
      done
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/app

  - name: sidecar-logger
    image: alpine:latest
    command: ["/bin/sh", "-c"]
    args: ["tail -f /var/log/app/transaction.log"]
    volumeMounts:
    - name: shared-logs
      mountPath: /var/log/app

  volumes:
  - name: shared-logs
    emptyDir: {}

```

Запустите мультиконтейнерный Под:

```bash
kubectl apply -f pod-sidecar.yaml

```

**Проверка логики работы Sidecar:**
Так как внутри Пода работают два контейнера, стандартная команда логов потребует явного указания имени целевого контейнера:

```bash
# Запрос логов из вспомогательного контейнера, читающего общий лог-файл
kubectl logs app-with-sidecar -c sidecar-logger -f

```

Вы увидите, как каждые 3 секунды Sidecar выводит транзакции, созданные основным приложением `main-app`.

## 🔍 Краткое руководство по диагностике (Troubleshooting)

* **Статус `ImagePullBackOff` или `ErrImagePull`:**
Контейнерный рантайм (`containerd`) на воркер-ноде не может скачать образ.
* *Решение:* Проверьте правильность написания тега образа. Если кластер находится в изолированном контуре (Air-Gapped), убедитесь, что образ предварительно загружен в локальный реестр или кэш ноды через `ctr` / `crictl`.


* **Статус `CrashLoopBackOff`:**
Образ успешно скачан, но процесс внутри контейнера мгновенно завершается с ошибкой.
* *Решение:* Контейнеру нужен постоянный фоновый процесс. Если вы запускаете пустой контейнер вроде `alpine` или `ubuntu` без бесконечного цикла (как в Шаге 4), он выполнит оболочку и сразу завершится. Проверьте вывод `kubectl logs <pod-name> --previous`, чтобы увидеть причину падения предыдущей итерации.
