# 🧪 Lab 4: Создание и управление Deployments

## 📋 Обзор

Эта лабораторная работа посвящена **Deployments (Развертываниям)** — главному контроллеру для управления приложениями без сохранения состояния (Stateless). Мы полностью развернем инфраструктуру в выделенном пространстве имен `work` и внедрим строгие политики выделения вычислительных ресурсов (CPU/Memory).

## 🎯 Цели

* Создать и использовать кастомный Namespace `work`.
* Описать и запустить декларативный `Deployment` с явным указанием `requests` и `limits`.
* Изучить механизм **Self-Healing** (самовосстановления) кластера в изолированном пространстве имен.
* Проанализировать поведение контейнеров при нехватке ресурсов и достижении лимитов (**OOMKilled**).

Перед запуском приложений необходимо подготовить для них изолированную среду.

**Выполнить на `k8s-master-01`:**

> ```

### Шаг 2: Создание манифеста Deployment со строгими лимитами

Мы напишем манифест веб-приложения на базе `nginx`. Основной упор делаем на блок `resources`, который сообщает планировщику (Scheduler), сколько гарантированно выделить ресурсов поду (`requests`) и выше какого порога ему запрещено прыгать (`limits`).

Создайте файл `deployment-web.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
  namespace: work
  labels:
    infra: production
    tier: frontend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: secure-web
  template:
    metadata:
      labels:
        app: secure-web
    spec:
      containers:
      - name: nginx-frontend
        image: nginx:1.25-alpine
        ports:
        - containerPort: 80
        resources:
          requests:
            memory: "64Mi"   # Минимально гарантированная память
            cpu: "100m"      # Минимальное процессорное время (0.1 ядра)
          limits:
            memory: "128Mi"  # Жесткий лимит памяти (выше — OOMKilled)
            cpu: "250m"      # Лимит CPU (выше — троттлинг/ограничение скорости)

```

Примените манифест:

```bash
kubectl apply -f deployment-web.yaml

```

### Шаг 3: Верификация размещения и инспекция лимитов

Убедимся, что наш Deployment создал подчиненный объект `ReplicaSet`, а тот, в свою очередь, развернул 3 пода с учетом наших ограничений.

```bash
# Проверка созданных ресурсов в нашем неймсейсе
kubectl get deployment,rs,pods -o wide

```

Вы увидите, что поды равномерно распределились по вашим воркер-нодам (`k8s-worker-01` и `k8s-worker-02`).

**Проверим, что лимиты применились на уровне контейнерного рантайма:**

```bash
# Замените имя пода на свое из вывода предыдущей команды
kubectl describe pod web-app-deployment-xxxxxxxxx-xxxxx

```

В выводе найдите блок:

```text
    Limits:
      cpu:     250m
      memory:  128Mi
    Requests:
      cpu:     100m
      memory:  64Mi

```

Кластер зарезервировал под эти поды суммарно минимум **192Mi** оперативной памяти и **300m** CPU на нодах.

### Шаг 4: Тестирование отказоустойчивости (Self-Healing)

Deployment непрерывно следит за тем, чтобы количество живых подов соответствовало полю `replicas: 3`. Давайте сымитируем аварию и удалим один из подов вручную.

```bash
# Включите мониторинг подов во втором терминале или запустите:
kubectl get pods

# Удаление одного случайного пода
kubectl delete pod web-app-deployment-xxxxxxxxx-xxxxx

# Мгновенная проверка состояния
kubectl get pods

```

**Что произошло:** Вы заметите, что удаляемый под перешел в статус `Terminating`, но в ту же секунду Deployment (через ReplicaSet) дал команду рантайму `containerd` развернуть новый под с новым уникальным хэшем, чтобы баланс системы оставался равен 3.

### Шаг 5: Декларативное масштабирование

Если нагрузка на веб-сервер выросла, мы можем изменить количество реплик. Правильный путь — редактирование кода.

Откройте `deployment-web.yaml`, измените значение `replicas: 3` на `replicas: 5` и примените изменения:

```bash
kubectl apply -f deployment-web.yaml

# Наблюдаем за докруткой кластера
kubectl get pods -w

```

Планировщик проверит, хватает ли свободных (не зарезервированных через `requests`) ресурсов на воркерах, и поднимет еще 2 пода.

## 🛟 Эмуляция аварии: Что будет, если контейнер превысит лимит? (Теоретический разбор и траблшутинг)

Когда вы работаете с ресурсами, важно понимать разницу в поведении процессора и памяти при перегрузках:

| Ресурс | Превышение `requests` | Превышение `limits` | Результат |
| --- | --- | --- | --- |
| **CPU** | Использует свободные излишки ноды | Контейнер исчерпал квоту времени | **Троттлинг.** Контейнер не падает, но начинает жутко тормозить (процессы искусственно замедляются). |
| **Memory** | Нода не трогает контейнер, пока есть общая память | Контейнер запросил больше, чем указано в лимите | **OOMKilled.** Ядро Linux (Out of Memory Killer) мгновенно завершает процесс внутри контейнера. Под падает. |

### Как это выглядит в логах при траблшутинге:

Если ваше приложение в пространстве имен `work` начнет течь по памяти, команда `kubectl get pods` вернет статус:
`STATUS: CrashLoopBackOff` или `OOMKilled`.

При выполнении `kubectl describe pod <имя_пода>` в блоке `Last State` вы увидите:

```text
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

```

> 🚩 **Exit Code 137** — это классический маркер того, что контейнер был принудительно убит операционной системой по сигналу `SIGKILL (9)` из-за нарушения лимитов памяти.
