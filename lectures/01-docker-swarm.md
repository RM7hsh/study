## Что такое Docker Swarm?

**Docker Swarm** — это встроенный инструмент Docker для **оркестрации контейнеров** и управления кластером машин.

### Ключевые характеристики:
- ✅ **Встроенный в Docker** — не требует отдельной установки
- ✅ **Простота** — легче для начинающих, чем Kubernetes
- ✅ **Нативная поддержка Docker** — работает с Docker CLI
- ✅ **Меньше ресурсов** — легче для маленьких проектов
- ✅ **Decentralized** — нет центрального компонента управления

## Архитектура Swarm

```
┌─────────────────────────────────────────────────────────────┐
│                    Docker Swarm Cluster                      │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌──────────────────┐      ┌──────────────────┐              │
│  │  Manager Node 1  │      │  Manager Node 2  │              │
│  │  (Leader)        │◄────►│  (Standby)       │              │
│  └──────────────────┘      └──────────────────┘              │
│           │                         │                         │
│           │   Raft Consensus        │                         │
│           └─────────────────────────┘                         │
│                     │                                          │
│           ┌─────────┼─────────┐                               │
│           │         │         │                               │
│  ┌────────▼───┐ ┌──▼──────┐ ┌▼────────────┐                 │
│  │Worker Node1│ │Worker N2│ │Worker Node 3│                 │
│  │            │ │         │ │             │                 │
│  │ Container  │ │Container│ │  Container  │                 │
│  └────────────┘ └─────────┘ └─────────────┘                 │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

### Уровни архитектуры:

#### 1. **Manager Nodes** (Управляющие узлы)
- Управляют состоянием кластера
- Хранят информацию о состоянии в распределенной БД (raft)
- Планируют задачи (scheduling) на worker nodes
- Обеспечивают высокую доступность

#### 2. **Worker Nodes** (Рабочие узлы)
- Запускают контейнеры (задачи)
- Подчиняются инструкциям manager nodes
- Не имеют доступа к управлению кластером

#### 3. **Services** (Сервисы)
- Логические единица для запуска контейнеров
- Можно масштабировать реплики
- Имеют встроенный load balancing

## Основные компоненты

### 1. **Swarm** (Кластер)
- Группа машин с установленным Docker
- Работают вместе как единое целое

### 2. **Node** (Узел)
```
Node Types:
├── Manager (2-3 для production)
│   ├── Принимает команды
│   ├── Управляет состоянием
│   ├── Хранит raft consensus DB
│   └── Может также быть Worker
│
└── Worker (остальные узлы)
    ├── Запускает контейнеры
    ├── Не может управлять кластером
    └── Слушает Manager
```

### 3. **Service** (Сервис)
```yaml
Service:
  - Описание желаемого состояния
  - Имя сервиса
  - Образ контейнера
  - Кол-во реплик
  - Порты
  - Переменные окружения
  - Volumes
  - Networks
```

### 4. **Task** (Задача)
- Экземпляр контейнера, запущенный на worker
- Одна задача = один контейнер
- Связана с одним сервисом

### 5. **Network** (Сеть)
```
Types:
├── overlay - для связи между nodes (кросс-хост)
├── bridge - для локальной коммуникации
└── host - прямой доступ к сети хоста
```

## Режимы работы узлов

### Replicated Mode (Реплицированный)
```
Service: web
Replicas: 3

Node1: web.1 (Container A)
Node2: web.2 (Container B)
Node3: web.3 (Container C)

Типичное использование:
- Web-приложения
- API сервисы
- Микросервисы
```

### Global Mode (Глобальный)
```
Service: monitoring-agent
Mode: global

Node1: monitoring-agent.xyz1 (Container)
Node2: monitoring-agent.xyz2 (Container)
Node3: monitoring-agent.xyz3 (Container)

Типичное использование:
- Мониторинг агенты
- Логирование агенты
- Security agents
```

## Ключевые концепции

### 1. **Desired State vs Actual State**
```
Ты описываешь DESIRED STATE:
$ docker service create --replicas 3 nginx

Swarm обеспечивает ACTUAL STATE:
- Если контейнер упадет → Swarm создаст новый
- Если узел отключится → Swarm переместит контейнеры
- Если много нагрузки → Swarm масштабирует
```

### 2. **Load Balancing (Встроенный)**
```
Внешний LB (Ingress):
Client → VIP:Port → Node1:Port
                 → Node2:Port
                 → Node3:Port

Внутренний LB (DNS):
service-name → DNS → Round Robin
```

### 3. **Self-Healing**
```
1. Контейнер упал
   → Manager обнаружил (health check)
   → Запланировал новый контейнер
   → Worker запустил новый контейнер

2. Worker Node отключился
   → Manager обнаружил отсутствие heartbeat
   → Переместил задачи на другие узлы
   → Восстановил требуемое кол-во реплик
```

### 4. **Rolling Update**
```
Обновление образа с нулевым downtime:

1. Старая версия v1: 3 контейнера
2. Получена команда обновления на v2
3. Manager поочередно:
   - Останавливает контейнер v1
   - Запускает контейнер v2
   - Проверяет health
   - Переходит к следующему
4. После обновления: 3 контейнера v2
```

## Сравнение с Kubernetes

| Параметр | Docker Swarm | Kubernetes |
|----------|-------------|------------|
| **Сложность установки** | ⭐ Очень просто | ⭐⭐⭐ Сложно |
| **Кривая обучения** | ⭐ Мягкая | ⭐⭐⭐ Крутая |
| **Масштабируемость** | До 1000-2000 узлов | До 5000+ узлов |
| **Production готовность** | ✅ Да | ✅ Да |
| **Сообщество** | ⭐⭐ Среднее | ⭐⭐⭐ Огромное |
| **Инструменты** | ⭐⭐ Встроенные | ⭐⭐⭐ Экосистема |

| **CLI команды** | docker service | kubectl |

## Когда использовать Swarm

### ✅ Используйте Swarm когда:

1. **Маленькие/средние проекты** (до 50 узлов)
2. **Простая инфраструктура** нужна
3. **Быстрое развертывание** приоритет
4. **Docker-first team** (знаете Docker хорошо)
5. **Ограниченные ресурсы** на управление
6. **Single Cloud Provider** нет необходимости

**Примеры:**
- Стартапы
- Тестовые окружения
- Внутренние сервисы
- DevOps practice/обучение

### ❌ Не используйте Swarm когда:

1. **Enterprise масштаб** (1000+ узлов)
2. **Сложная оркестрация** нужна
3. **Multi-cloud** требуется
4. **Production SLA** 99.99%+
5. **Сложный networking** нужен
6. **Kubernetes ecosystem** критичен

**Примеры:**
- Большие корпорации
- Cloud-native приложения
- Микросервисная архитектура (100+)
- Требуется StatefulSets

## Состояние объектов Swarm

```
┌─────────────────────────────────┐
│      Node States                │
├─────────────────────────────────┤
│ UNKNOWN  - информация потеряна  │
│ DOWN     - узел недоступен      │
│ READY    - узел готов работать  │
│ DISCONNECTED - потеря связи     │
└─────────────────────────────────┘

┌─────────────────────────────────┐
│      Task States                │
├─────────────────────────────────┤
│ NEW          - только создана   │
│ PENDING      - ожидает запуска   │
│ ASSIGNED     - назначена узлу   │
│ ACCEPTED     - узел согласен    │
│ PREPARING    - готовится        │
│ RUNNING      - запущена         │
│ EXITED       - завершена        │
│ FAILED       - ошибка запуска   │
│ SHUTDOWN     - выключается      │
│ ORPHANED     - потеряна связь   │
│ REMOVE       - удаляется        │
└─────────────────────────────────┘
```

## Основные команды Swarm

```bash
# Инициализация кластера
docker swarm init

# Информация о кластере
docker info
docker node ls

# Создание сервиса
docker service create --replicas 3 --name web nginx

# Просмотр сервисов
docker service ls
docker service inspect web
docker service logs web

# Масштабирование
docker service scale web=5

# Обновление
docker service update --image nginx:latest web

# Удаление
docker service rm web
```
